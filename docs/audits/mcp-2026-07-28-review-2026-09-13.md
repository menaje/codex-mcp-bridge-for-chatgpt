# Historical MCP 2026-07-28 gap review

> This is the pre-implementation baseline recorded on 2026-09-13. It describes
> the SDK v1 bridge that existed then and is not the current product contract.
> See [the migration guide](../mcp-2026-07-28-migration.md) and

> the implemented v2/current-only result.

검토일: 2026-09-13, Asia/Seoul. 대상은 `codex-mcp-bridge-for-chatgpt` 0.4.1, 로컬 `dev` 커밋 `590fde9159d4de562f95252282f27db7be3233f2`이다. `package-lock.json`과 설치된 SDK는 모두 `@modelcontextprotocol/sdk` 1.29.0이었다. 공식 MCP의 현재 규약은 **2026-07-28**이다. [공식 버전 정책](https://modelcontextprotocol.io/docs/2026-07-28/learn/versioning)

후속 결정: **2026-07-28 단일 규약으로 전면 전환한다.** 사용자의 2026-09-13 결정에 따라 구·신규 동시 지원 제안을 대체했으며, 구형 처리·자동 fallback을 제거하는 범위와 완료 기준을 [이슈 #105](https://github.com/menaje/codex-mcp-bridge-for-chatgpt/issues/105)에 등록했다.

**판정: 기존 2025 규약 경로는 검증한 범위에서 동작하지만, 2026-07-28 규약은 지원하지 않는다.** 기본 설정의 `stateless`는 요청마다 구형 SDK 서버를 만드는 구현 방식이다. 최신 규약의 요청별 메타데이터·발견 절차를 구현했다는 뜻은 아니다. 운영 ChatGPT 연결이 현재 고장 났다는 판단은 이 검토에 포함하지 않는다.

검토는 소스, 공식 문서, 기존 테스트와 임시 DB·가짜 upstream을 사용한 loopback HTTP 요청으로 수행했다. 운영 터널, 실행 중인 Codex 작업, 실제 프로젝트 설정은 변경하지 않았다. 제품 코드 수정 없이 이 검토서만 추가했다.

**우선 대응할 차이**

| 항목 | 현재 구현과 증거 | 최신 규약과 영향 | 우선순위 |
| --- | --- | --- | --- |
| 버전·발견·요청 처리 | SDK 1.29.0의 최신 버전 상수는 `2025-11-25`. `server/discover` 없음. [server.ts](../../src/server.ts) 402, 755행 | 최신 클라이언트의 발견과 직접 도구 요청이 거부됨. 최신 지원의 선행 작업 | 높음 |
| 결과와 목록 캐시 | 실제 `tools/list` 결과는 `{tools}`, `resources/list`는 `{resources}`. `resultType`, `ttlMs`, `cacheScope` 없음 | 새 규약 결과 스키마 및 캐시 계약에 맞는 직렬화 필요 | 높음 |
| HTTP 세션·알림·재연결 | 선택적 stateful 모드는 세션 ID, GET 스트림, 이벤트 재생 사용. [server.ts](../../src/server.ts) 112, 698, 786행 | 최신 경로에 같은 방식을 적용할 수 없음. 목록 변경 알림을 제공한다면 `subscriptions/listen`으로 연결 | 높음, stateful 사용 시 |
| HTTP 요청 헤더 | `Mcp-Method`·`Mcp-Name`와 본문의 일치 검증 없음 | 최신 경로에서 필수 헤더와 본문 검증을 함께 도입해야 함 | 높음, 최신 경로 도입 시 |
| 장기 작업·사용자 입력 | 브리지 고유 Activity/Agent/Job, `codex_status`, 질문 카드 사용 | Tasks·MRTR 표준 연동은 추가 가능. 선택 확장이므로 미구현 자체가 핵심 규약 위반은 아님 | 후속 |

새 규약은 `initialize`/`notifications/initialized`를 없애고 요청마다 버전과 클라이언트 capabilities를 받는다. 서버의 `server/discover` 구현은 필수지만 클라이언트가 먼저 호출할 의무는 없다. 따라서 발견 호출만 추가하고 이후의 도구 호출에 초기화를 요구하는 수정으로는 충분하지 않다. [버전 선택과 발견](https://modelcontextprotocol.io/docs/2026-07-28/learn/versioning)

일반 결과에는 `resultType: "complete"`가 필요하고, 목록 및 해당 리소스 결과에는 캐시 필드가 필요하다. 현재 `content`·`structuredContent`를 함께 제공하는 도구는 활용할 수 있으나, 그 외곽의 MCP 결과 계약을 갱신해야 한다. 코드의 Job 보존용 `ttlMs`는 목록 캐시 TTL과 다른 개념이다. [도구 결과와 캐시 예시](https://modelcontextprotocol.io/specification/2026-07-28/server/tools), [캐시 대상 변경](https://modelcontextprotocol.io/specification/2026-07-28/changelog)

최신 HTTP 요청은 `MCP-Protocol-Version`, `Mcp-Method`, 해당 메서드에 필요한 `Mcp-Name`을 요구한다. 헤더와 본문이 어긋나면 `400 / -32020`으로 거부해야 한다. 현재는 새 버전 자체를 거부하므로, 이 항목은 현재 경로의 새 공격을 입증한 것이 아니라 최신 지원 구현 시 필요한 검증이다. `x-mcp-header`는 서버가 선택적으로 사용하는 기능이므로 무조건 추가할 필요는 없다. [HTTP 헤더 계약](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http)

최신 규약에서는 HTTP 프로토콜 세션, GET 알림 스트림, `Last-Event-ID` 기반 재전송이 제거됐다. SSE 자체는 계속 사용한다. 이 프로젝트는 단일 규약 전환 결정에 따라 구형 호환 경로를 제거한다. [전송 변경](https://modelcontextprotocol.io/specification/2026-07-28/changelog)

**별도로 확인한 기존 누락: HTTP Origin 검증**

[server.ts](../../src/server.ts) 456행의 Express 생성은 Host를 검증하지만 Origin 정책을 지정하지 않는다. 698행과 758행의 SDK transport에도 Origin 검증 옵션이 없다. SDK 1.29.0 transport의 DNS rebinding 보호 옵션 기본값은 비활성이다.

임시 서버에 정상 테스트 Bearer 인증을 넣고 `Origin: https://untrusted-origin.invalid`로 `tools/list`를 요청했을 때 stateless와 stateful 모두 **HTTP 200**을 반환했다. Origin 허용 정책이 없다는 재현이다. 인증 우회, 실제 브라우저 공격 또는 운영 환경 악용 가능성을 입증한 테스트는 아니다.

유효하지 않은 Origin을 403으로 거부하는 요구는 이미 2025-11-25에 존재했다. 따라서 이번 개정으로 생긴 회귀와 구분하여 수정할 항목이다. Origin 없는 네이티브/터널 요청과 명시적으로 허용한 Origin을 지원하면서, 그 외의 Origin을 거부하는 경계가 필요하다. [2025년 전송 요구사항](https://modelcontextprotocol.io/specification/2025-11-25/basic/transports)

**이미 맞는 방향으로 구현된 부분**

- **Codex 실행:** 기본 backend는 `app-server`이고 [upstreamRouter.ts](../../src/upstreamRouter.ts) 40행은 다른 backend의 새 실행을 거부한다. 공식 문서에서 제거된 `codex mcp-server` 대신 App Server 사용을 안내하는 방향에 이미 맞는다. 보존된 옛 backend 식별자는 이 실행 경로가 아직 사용된다는 증거가 아니다. [공식 Codex SDK 문서](https://learn.chatgpt.com/docs/codex-sdk)
- **MCP Apps 카드:** [tools.ts](../../src/tools.ts) 7833행은 `_meta.ui.resourceUri`와 visibility를, [settingsCard.ts](../../src/settingsCard.ts) 17행은 `text/html;profile=mcp-app`을 사용한다. `ui/initialize`와 `postMessage` RPC도 구현되어 있다. 다만 [cardBrowserRuntime.ts](../../src/cardBrowserRuntime.ts) 27행은 `window.openai.callTool`이 있으면 이를 우선하므로 완전한 표준 우선 구현은 아니다. 호환 alias는 계속 지원되지만 새 UI는 공유 MCP Apps 방식을 우선하라는 공식 권고와 비교할 후속 개선점이다. 현재 읽기/쓰기별 재시도 경계를 유지하며 검토해야 한다. [공식 UI 가이드](https://developers.openai.com/plugins/build/chatgpt-ui)
- **UI 초기화와 핵심 MCP 초기화는 별개:** 핵심 규약에서 `initialize`가 없어졌다는 이유로 카드의 `ui/initialize`를 제거하면 안 된다. MCP Apps UI bridge에는 자체 초기화 절차가 있다. [공식 UI bridge 설명](https://developers.openai.com/plugins/build/chatgpt-ui)
- **업무 상태:** Activity/Agent/Job 및 프로젝트 selector는 애플리케이션 상태다. 프로토콜 세션 제거 때문에 없앨 대상이 아니다. [scopeResolver.ts](../../src/scopeResolver.ts) 61행의 호스트 메타데이터 기반 대화 범위도 `Mcp-Session-Id`와 별개다. 새 전송 어댑터가 OpenAI 메타데이터와 기존 권한 검증을 보존해야 한다. [공식 개정 설명의 애플리케이션 handle 원칙](https://blog.modelcontextprotocol.io/posts/2026-07-28/)

**선택 기능과 추가 검증 범위**

Tasks는 `io.modelcontextprotocol/tasks` 확장이다. 장기 작업을 durable handle로 반환하고 `tasks/get`으로 결과를 읽으며 `tasks/update`로 입력을 제공한다. 현재의 Job 저장·조회 경계 위에 표준 어댑터를 붙일 후보지만 Activity의 목표·검증 수명주기까지 표준 Task와 동일시하면 안 된다. 이 확장이 채팅 응답 종료 후 모델을 자동으로 다시 실행해 주는 것도 아니다. 호스트가 확장을 지원하는지 별도 확인이 필요하다. [공식 Tasks 설명](https://modelcontextprotocol.io/extensions/tasks/overview)

MRTR는 추가 입력을 `resultType: "input_required"`로 반환하고 `inputResponses`와 필요한 `requestState`를 받아 원 요청을 재개하는 방식이다. 브리지의 일반 질문 카드와 자동으로 같아지는 계약은 아니다. 특히 [mcpElicitation.ts](../../src/mcpElicitation.ts) 6행의 URL `elicitationId` 요구는 [appServerUpstream.ts](../../src/appServerUpstream.ts) 1877행의 **Codex App Server 내부 요청**에 적용된다. 최신 MCP에서 해당 필드가 제거됐다는 이유만으로 이 내부 계약을 바로 변경해서는 안 된다. 실제 App Server 전달 형식을 검증한 뒤 판단해야 한다. [MRTR와 URL elicitation 변경](https://modelcontextprotocol.io/specification/2026-07-28/changelog)

OAuth는 DCR보다 CIMD를 권장하고 issuer 관련 검증을 강화했다. 이 중 issuer 검증·자격증명 저장은 OAuth 클라이언트, CIMD 지원은 클라이언트 및 인가 서버의 역할을 구분해야 한다. 현재 브리지는 private Bearer/Tunnel 배치이고 [server.ts](../../src/server.ts) 505행의 OAuth discovery는 의도적으로 404다. 일반 OAuth MCP endpoint로 확장한다면 protected-resource metadata와 토큰 검증 경계를 따로 구현해야 한다. 현재 private tunnel 사용만을 이유로 브리지에 전체 OAuth 서버를 추가할 필요는 없다. [공식 인가 규약](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization), [공식 Secure MCP Tunnel 문서](https://developers.openai.com/api/docs/guides/secure-mcp-tunnels)

OpenAI의 서버 제공 Skills 지원도 확인했다. `capabilities.extensions`의 `io.modelcontextprotocol/skills`, `skills/list`, `skills/get`, 리소스 digest를 이용한 제출 시점의 정적 가져오기다. 공식 문서는 아직 SEP-2640 초안의 제한된 지원이라고 명시한다. 브리지에는 해당 구현이 없지만 필수 호환성 결함으로 분류하지 않는다. [공식 MCP 서버 문서](https://developers.openai.com/plugins/build/mcp-server)

**검증 결과**

기존 테스트 실행:

```sh
./node_modules/.bin/vitest run test/server.test.ts test/stdioServer.test.ts test/scopeResolver.test.ts --maxWorkers=3
```

Vitest 결과는 **6 files / 74 tests passed**, 28.78초다. 지정 필터가 선택한 테스트의 결과이며 전체 테스트·실제 ChatGPT·실제 터널 호환성을 검증한 결과는 아니다.

격리 HTTP probe는 실제 `createHttpServer`를 임의 loopback 포트에서 실행하고 임시 SQLite, 가짜 model catalog, 실행을 거부하는 가짜 upstream을 사용했다. 요청별 SSE 응답에서는 빈 priming event를 건너뛰고 RPC ID가 일치하는 최종 응답을 확인했다.

| 요청 | 기본 stateless | 선택적 stateful |
| --- | --- | --- |
| `server/discover`, 최신 버전 헤더·요청 메타데이터 포함, 초기화 전 | 400 / -32000, unsupported protocol version | 400 / -32000, session header required |
| `tools/list`, 최신 버전 헤더·요청 메타데이터 포함, 초기화 전 | 400 / -32000 | 400 / -32000 |
| `server/discover`, 버전 헤더 없는 구형 서버 탐색용 probe | 200 / JSON-RPC -32601 | 400 / session header required |
| `initialize`, `2025-11-25` | 200, 해당 버전 반환 | 200, 해당 버전과 세션 ID 반환 |
| 구형 초기화 후 `tools/list` | 200, 31개 도구 | 200, 31개 도구 |
| 구형 초기화 후 `resources/list` | 200, 8개 리소스 | 200, 8개 리소스 |
| 읽기 도구 `codex_settings` | 200, content/structuredContent/_meta | 200, content/structuredContent/_meta |
| 정상 테스트 인증 + 외부 Origin의 `tools/list` | 200 | 200 |
| 구형 초기화 후 `2026-07-28`의 `tools/list` | 400 / unsupported protocol version | 400 / unsupported protocol version |

양쪽 모드에서 성공한 목록·도구 응답에는 `resultType`이 없었고 목록에는 `ttlMs`·`cacheScope`도 없었다. 이것은 구형 규약으로 응답한 결과이며, 구형 클라이언트에게도 해당 필드가 반드시 있어야 한다는 주장이 아니다.

최신 요청의 핵심 형식은 아래와 같다. 이 probe는 운영 서버에 전송하지 않았다.

```http
POST /mcp
Accept: application/json, text/event-stream
Content-Type: application/json
MCP-Protocol-Version: 2026-07-28
Mcp-Method: tools/list

{"jsonrpc":"2.0","id":1,"method":"tools/list","params":{"_meta":{"io.modelcontextprotocol/protocolVersion":"2026-07-28","io.modelcontextprotocol/clientCapabilities":{},"io.modelcontextprotocol/clientInfo":{"name":"local-review-probe","version":"1"}}}}
```

패키지 조회 시 v1의 최신은 1.30.0, 분리된 `@modelcontextprotocol/server`의 최신은 2.0.0이었다. 1.30.0 공식 npm 배포 tarball의 `dist/esm/types.js`도 최신 규약 상수가 **2025-11-25**임을 직접 확인했다. 따라서 1.29.0에서 1.30.0으로의 갱신만으로 이번 차이를 해소할 수 없다. [확인한 공식 SDK 배포물](https://registry.npmjs.org/@modelcontextprotocol/sdk/-/sdk-1.30.0.tgz)

**권장 변경 순서와 수용 기준**

1. **Origin 누락을 독립 수정한다.** 허용 Origin, 거부 Origin, Origin 없는 native/tunnel 요청을 검증한다. 현재 보호 중인 Host·인증 검사를 함께 유지한다.
2. **2026-07-28만 처리하는 전송 어댑터로 교체한다.** SDK v2의 `createMcpHandler` 및 stdio `serveStdio`에서 legacy 지원을 명시적으로 거부한다. 구형 초기화·세션·재전송·모드 분기와 자동 fallback은 제거한다. 기존 공통 application service·SQLite·권한·도구 계약은 재사용한다. v2 패키지만 설치하거나 직접 만든 `McpServer`를 그대로 연결하면 자동으로 최신 규약을 사용하는 것은 아니다. [SDK 마이그레이션](https://ts.sdk.modelcontextprotocol.io/v2/migration/support-2026-07-28)
3. **직렬화·헤더·캐시·알림을 함께 검증한다.** 초기화 없는 최신 `tools/list`/`tools/call`, `server/discover`, 올바른 버전 오류, 헤더 불일치 거부, 결과 스키마, private 캐시 정책, 제공하는 목록 알림을 수용 기준으로 삼는다. 실제 도구 스키마와 app 전용 visibility가 보존되는지도 확인한다.
4. **재연결 시 실행 중복을 방지한다.** 새 JSON-RPC ID와 기존 논리 `requestId`를 구분한다. 새 전송의 취소 신호를 브리지 Job 강제 종료에 곧바로 연결하지 말고, 관측 요청 취소·업무 취소의 계약을 분리하여 기존 중복 실행 방지와 명시적 취소 권한을 보존한다.
5. **최신 규약 단독 동작과 실제 터널을 검증한다.** 최신 버전 고정 클라이언트의 성공, 구형 규약의 명시적 거부, UI 카드, 대화 범위 격리, 재시도와 재시작을 확인한다. 실제 ChatGPT/Tunnel에서 최신 규약으로 성공해야 하며 자동 fallback 성공을 완료 증거로 인정하지 않는다. 호스트 미지원은 배포 blocker로 기록하고 구형 경로를 재도입하지 않는다. 이번 조사에서는 v2 클라이언트 및 실제 ChatGPT/Tunnel의 협상까지 실행하지 않았다. [SDK 협상 동작](https://ts.sdk.modelcontextprotocol.io/v2/protocol-versions)
6. **Tasks/MRTR·UI 표준 우선·서버 Skills는 그 다음에 평가한다.** 호스트 지원과 기존 사용자 흐름을 확인한 뒤 필요한 기능을 선택한다.

현재 대화의 작업 디렉터리인 `coni-memory`는 별도 MCP 서버다. 그 `src/adapters/mcp.ts` 31행도 **2025-06-18**을 고정 반환하며 초기화가 필요하다. 최신 규약을 목표로 한다면 그 어댑터도 별도 대응 대상이다. 이 검토의 HTTP 재현 및 테스트 수치는 `codex-mcp-bridge`에 대한 것이다.
