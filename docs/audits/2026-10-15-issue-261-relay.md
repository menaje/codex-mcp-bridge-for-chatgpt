## Implemented contract (W1–W3)

The [Relay contract](../relay-delivery.md) documents the public behavior and
upgrade boundary. `relayCard.ts` supplies a zero-height blank resource at
`ui://codex-mcp-bridge/relay/v1.html`, generation 1. Task/answer association and
opening metadata are automatic in the default server profile. Internal waits,
mutations, ACKs and status/receipt reads never recursively create cards.

`relayDelivery.ts` uses the existing `bridge_meta` journal and admission Unit of
Work. One current Activity/card owns pre-entry claims. A separate durable entry
grants dispatch only once. Sending, accepted and unknown attempts never rearm on
lease expiry, remount, takeover or restart. ACK loss retries only the identical
attempt's recording. Only structured explicit no-send rejection can take the
bounded retry path; error text is not evidence. Standard and compatibility host
message APIs are selected before sending, without a post-send fallback.

Current host scope, authenticated principal and project identity authorize each
operation. Correlation references are not capabilities. Messages carry common
receiver guidance plus lookup references, not original result/question bodies,
answers, secrets or project paths. Dynamic continuation remains subject to the
existing admission, Agent/context, model and permission checks. A receipt binds
the immutable payload and canonical request atomically with B's admission and
Relay enrollment. Distinct parallel steps remain distinct. Exact receipt pages
are bounded to 24 entries with an indexed cursor.

Current questions and approvals, including nonblocking questions, have stable
events through unrelated progress. Send entry rechecks current source identity;
answer dispatch rechecks the existing questionRef and worker generation. Relay
stop, followup stop, Job cancellation and final Activity completion remain
separate. One terminal Job, result offer or accepted notice never finishes a
default manual Activity.

Readiness is emitted after commit. Recovery reads at most 32 registered Jobs per
page; readiness reads at most 64 references; waits are bounded to 25 seconds,
eight per store and two per goal. Empty reads do not create writer transactions.
There is no per-progress global scan or external Events dependency. Capacity
archival preserves still-retained originals; common expiry and project deletion
remove Relay references without removing minimal stop/replay intent.

## Review and functional evidence (W4)

A separate code-review pass checked the authority, persistence, replay, cost and
transition boundaries. Findings repaired before integration included retained
result recovery after registry eviction, canonical naming for unnamed dynamic
Agents, malformed RPC response handling, same-conversation principal checks for
question reads/answers, nonblocking question notification and the explicit
Events profile's card-free default. This is an implementation-agent review and
automated regression record, not a claim of an independent reviewer approval.

They do not launch a real Codex work session or modify operational settings.

The last two cases demonstrate the limit of server refusal: an old in-memory
sender still requires actual iframe teardown. Already-posted host messages are
not retroactively revoked.

No duration/soak job, shorter substitute or accelerated continuous-operation
test was introduced. Functional fixtures directly construct protocol states,
retention states and event ordering; host request deadlines test uncertainty.
The existing one-minute task test was not run. Full unfiltered validation was
therefore not claimed. Real GPT automatic resumption and real A→review→B
acceptance remain outside #261's completion criteria, as explicitly requested.
The blank document and size request do not establish invisible host containers,
invisible messages, iframe survival while the app is closed or conversation-wide
exactly-once delivery. No user observation or additional approval is a gate for
this implementation.
