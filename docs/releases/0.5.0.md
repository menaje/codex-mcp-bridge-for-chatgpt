# Codex MCP Bridge for ChatGPT 0.5.0

This release updates the Bridge's protocol, work execution and retention
contracts, native settings, and ChatGPT cards. It includes breaking changes from
0.4.1; deploy the matching server and macOS app together and refresh the ChatGPT
connection before starting new work.

## Work, results and history

- Tasks use one durable asynchronous admission contract. Recover an admitted
  Job with its original request identity, read its exact result, and continue
  within the user's existing goal and approvals.
- New ordinary Jobs and question answers automatically attach the blank goal
  relay. Durable delivery claims and idempotent followups protect against
  duplicate execution. Host rejection stops automatic relay retries; pending
  questions, approvals, and explicit stops retain their authority.
- The native Dashboard separates In progress, Execution history and Problem
  history. The ChatGPT card calls execution history Run history. Lists group
  Activity, Agent and individual runs, show recorded failure/cancellation
  reasons, and append pages through Show more.
- One saved 7-, 30-, 90-day or unlimited policy covers sanitized result bodies,
  summaries and related history. Connection idle release and in-memory registry
  limits remain separate. Missing originals from earlier versions remain
  explicitly partial.
- Independent execution, state and read processes keep controls responsive
  during observation or storage outages. Bounded recovery preserves exact Job
  ownership, replay protection and user stop intent.
  Completed questions coalesce into current-input recovery snapshots, so long
  turns do not exhaust live-event capacity through resolved question history.

## Settings, accounts and reusable procedures

- Choose the Codex installation separately from its authentication connection.
  Reuse an existing login, prepare a separate ChatGPT login, or explicitly select
  a Bridge API-key connection. Login preparation preserves the existing shared
  account and uncertain credential writers remain fenced until exit.
- New authentication profiles can share Bridge-owned conversation storage;
  conversation persistence and Codex app visibility are independent choices.
  Existing profiles retain their original storage.
- Processing speed offers Standard and Fast. Ultrafast is hidden until access
  can be verified; current CLI contracts cannot provide that confirmation.
  Older speed settings retain their behavior until explicitly changed. Selected
  speed and accepted requests do not prove the actual processing tier.
- Fixed and automatic model policies use the available catalog, shared reasoning
  choices, editable model descriptions and description history.
- Bridge skills use versioned SKILL.md content with attached Markdown files.
  The native library supports import, editing, version restore and export.
  Retrying a committed package import or update recovers its saved result without
  requiring another upload or creating an extra version.
  Cached attachment selections reject older read responses, and isolated native
  operations carry supported large skill content and exports.
  The native management list includes every active and archived skill.
- Shared translations, IME-aware native editors, guarded edit sessions and
  refreshed English screenshots improve settings and library use.

## Projects and startup

Archive blocks new project work, stops project-owned execution and confirms
context cleanup. Unresolved cleanup remains visible and retryable. Restore
retains the registration identity and starts fresh execution context on next use.
After confirmed archive, deletion removes Bridge management and work records;
the actual folder, files, Git repository and original Codex/ChatGPT conversations
are preserved. Registering that folder again creates a new identity.

Configured initial startup can retry confirmed temporary readiness failures
within one five-minute budget and three total attempts. Explicit stop and
cancellation take priority. Native reads preserve confirmed content through
temporary failures and fence stale responses after connection changes.

Malformed HTTP request URLs return a client error and keep the server running.

Release readiness fixes include Linux kernel-process observation, native Swift
build compatibility, and adoption of an existing runtime when its requested
configuration becomes unreadable. Updated MCP SDK, Hono and Zod dependencies include
current security fixes; bounded HTTP bodies and structured tool inputs limit
validation resource use.
Native control sockets assemble large requests without repeated full-buffer
copies. Process cleanup retains its last observation when a wait stage expires
and requires a fresh observation and ownership check before escalation.

## Upgrade from 0.4.1

1. Use a client supporting MCP 2026-07-28. Legacy MCP initialization, session
   transport, tool aliases and task modes are rejected. Current task input uses
   contract version 6 and the exact advertised execution envelope reference.
2. Stop database owners and follow the [state upgrade runbook](../state-upgrade-recovery.md).
   The target is schema 32, with supported sources 3 through 31 and a verified
   private pre-upgrade backup. Schema 1/2 and retired standalone JSON stores are
   unsupported. Once service has opened, use forward repair or explicit data
   reconciliation rather than restoring an earlier snapshot automatically.
3. Update native clients with the server. The local companion protocol is 12
   and the remote companion protocol is 10. Reconnect or restart clients.
4. Close old card instances, refresh ChatGPT connector discovery, and reopen
   current cards: Settings v6 and Dashboard v5. Relay v1 attaches to the next
   ordinary task or answer. Retired Decision Cards cannot submit or retrieve
   results; preserve any needed decision in the conversation.
5. Use current skill `content` fields and issued followup references. Preserve
   existing request identities and receipts when recovering work; unexecuted
   legacy followups require explicit reapproval under the transition rules.

Experimental OAuth/MCP Events configurations remain separate from ordinary
delivery. Isolated tests and historical acceptance records do not establish
support for every host, account, billing or entitlement combination.
