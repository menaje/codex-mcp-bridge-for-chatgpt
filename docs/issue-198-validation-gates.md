# #198 cumulative regression and candidate validation

The integration target is `dev`. This gate combines existing tests for the #200 execution/storage/delivery distinction, #196 request capacity, and #197 storage audit. It does not install or replace the operating application. A passing fixture is evidence for the boundary it actually exercised, not for a live ChatGPT or Codex account.

## Run the three stages

| Stage | Command | When and meaning |
| --- | --- | --- |
| Related change | `npm run test:issue-198:quick` | Release and pinned App Server compatibility check, selected product-path tests, #197 disposable WAL/lock probe. Run during implementation. |
| Integration candidate | `npm run test:issue-198:integrated` | Full Node build/tests, macOS Swift tests, MCP conformance, #193 scale characterization, #196 saturation, #142/#143 isolation, #185/#186/#189 execution/observation/retention, #197 storage, #137 wait and #138 state access. Run from the source candidate, preserving every first-run result. |
| Installed candidate bundle | `npm run test:issue-198:installed` | Requires clean committed source. Builds and signs a **separate** `.app`, checks embedded commit/source hash/schema/dependency/manifest identity and signature, then runs #185/#186/#189 against bundled JavaScript and bundled dependencies with disposable state and synthetic App Server. `--bundle <app>` may select an already built exact candidate. |

The App Server schema check needs the repository's CI baseline Codex CLI, currently `0.153.3`. Point `CODEX_MCP_BRIDGE_CODEX` at that executable for quick and integrated stages. A newer user CLI is not substituted for the reproducible schema pin; its failure remains in the result. The runner records the observed CLI version. It accepts `--output-dir <directory>` only when that directory does **not** exist; an existing directory is rejected before any report or log is written. By default, each run reserves a unique `output/issue-198/<stage>-<timestamp>-<random>/` directory. Each run writes `results.json`, `report.md` and one raw log per scenario. `output/` is ignored by Git. The JSON records source SHA and source hash, dirty state, OS/CPU/Node/SQLite/driver/schema, commands, timing, sample summaries where supplied by the original script, exit result and log hash. It reports unrun external/operating boundaries explicitly. Report updates are atomic; a log creation or write failure makes the run fail and records the interruption separately when the filesystem permits it. There is no automatic retry and a failing required scenario makes the stage fail after retaining the evidence.

The runner removes any inherited `CODEX_TEST_BUNDLE_DIST` from quick and integrated scenarios, including the #185/#186/#189 product regressions. The installed stage also clears an inherited selector while building and only injects the verified candidate's runtime path after the bundle identity gate. Each #185/#186/#189 result must report `runtime: "source"` for integrated or the exact verified bundle path for installed; a missing or different actual runtime fails that scenario even if its command exits 0.

The installed stage verifies the bundle's embedded build commit and source hash against the clean checkout, schema 29 and packaged manifest/dependencies against the same checkout. It checks the strict code signature. It does **not** launch the actual GUI, migrate the user's DB, use the user's project/Job, or assert that the currently installed app is on the candidate revision. Deployment is a separate gate.

## Interpretation and approval rules

1. **Identity before metrics:** source SHA/hash, schema, actual #185/#186/#189 runtime and bundle build info must match the selected stage. Bundle validation requires a clean tracked checkout. Missing or mismatched identity fails the scenario or installed stage.
2. **Correctness before speed:** a failed scope/authority check, duplicate Job/turn, wrong terminal result, early result ACK, lost due retry or starved management lane fails the stage regardless of SQL count or median latency. Newly admitted work requires durable admission; an existing execution remains independent of state-owner observation delay.
3. **Sample size:** a p99 needs at least 100 observed calls under the named fixture. #185 now measures 100 product MCP exact input and 100 exact terminal status/result calls after warmup. #143 samples at least 100 health responses under a 30-second stopped runtime. #142 reports an observed maximum instead of labeling a 25-call healthy command sample as p99. #193's single synthetic scale run and #196's 20 missing-Job queries have no p99 claim. Percentiles compare only the declared fixture, not all hosts.
4. **Existing targets:** under the stated state-fault condition, `/healthz` p99 is below 200 ms and ingress event-loop delay p99 below 50 ms when at least 100 samples exist; healthy state command duration is below 500 ms under a normal DB. #142's existing assertions check these fixture targets. Deliberately locked writes are judged by explicit uncertainty/busy and later recovery, not a 500-ms normal-write target. Actual external end-to-end limits are not inferred from these numbers.
5. **Performance attribution:** report SQL count/hydrated rows as supported proxies only. Distinguish queue, SQL plus mapping, commit boundary, IPC, response bytes, WAL frames and physical file size. Do not infer SQLite internal page count or `fsync` duration. Any baseline/candidate comparison must use the same fixture and machine; historic #193 figures are context, not a fresh side-by-side result.
6. **First failures and skips remain visible:** no auto retry erases an initial failure. A rerun uses a different output directory and retains the original report and log. An explicit directory already containing evidence is rejected before writing. Lack of real Codex/ChatGPT/Tunnel or actual operating cutover stays `unrun`; development integration may finish while deployment approval remains separate.

The machine report's `passed-with-declared-limits` verdict means every scenario in **that stage** exited successfully and all listed omissions remain in scope only for later acceptance. It never means the operating app was updated or a real user Job was tested.
